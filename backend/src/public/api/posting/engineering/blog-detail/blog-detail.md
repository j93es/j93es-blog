## 0. 들어가며

프론트엔드 엔지니어로써 차별점을 지닐 수 있는 방식에는 무엇이 있을까요? 화려한 UI 구현, 최신 기술 적용 등 여러 좋아보이는 방안이 있을 겁니다. 그런데 저는 조금 다르게 바라보고 싶습니다. 기본에 충실한, 목적에 부합하는 엔지니어링이 오히려 그 웹사이트를 돋보이게 만들 수 있지 않을까요? 화려함을 추구하는 오늘, 저는 정제된 아름다움을 추구하고 싶습니다.

그렇다면 정제된 아름다움이란 무엇일까요? 목적 외의 추가적인 것을 제하는 것이 중요하다고 생각합니다. 그리고 남은 리소스로 디테일을 챙기는 것이 중요한 것 같습니다. 챙겨야할 디테일을 챙기지 않고, 화려함만을 추구하는 것은 제가 추구하는 엔지니어링을 아닌 것 같습니다.

그렇다면 프론트엔드에서 챙겨야할 디테일에는 무엇이 있을까요? 제가 블로그를 개발하며 겪은 경험을 바탕으로 프론트엔드에서의 디테일에 대해 살펴보겠습니다.

## 1. 프로젝트 소개

이 글을 보고 있는 블로그가 본 포스팅에서 소개할 프로젝트입니다. 블로그의 본질은 무엇일까요? 결국 글을 읽는 것이라고 생각합니다. 그렇다면 어떤 환경이 글을 읽기에 좋은 환경일까요? 저는 책과 같은 깔끔함을 추구하는 것이 좋다고 생각합니다. 여러 블로그들을 살펴본다면, 이미지들로 인하여 조금은 난잡하다는 느낌이 드는 경우가 종종 있습니다. 그렇기에 저는 난잡함을 줄이고 깔끔하다는 인상을 주는데에 그 목적으로 맞추었습니다. 즉, 정제된, 절제된 아름다움을 추구하고자 하였습니다.

특히 완성도 있게 프론트엔드를 구성하려하였습니다. 그렇기 위해서는 프론트엔드에서 디테일을 챙기는 작업이 필요하겠지요. 이제부터는 완성도 있는 프론트엔드를 위한 디테일을 살펴보겠습니다.

## 2. favicon, logo

favicon 웹페이지에 적절히 적용하셨나요? favicon은 브라우저의 주소창이나 탭에 표시되는 이미지 입니다. 해당 이미지로 웹사이트에 대한 인상을 심어주기도 합니다. 그런데 생각보다 많은 분들께서 이러한 favicon을 기본 템플릿 그대로 사용하기도 합니다. 웹페이지가 완성도 있게 구성되었다는 느낌을 주기 위해서는 favicon 또한 잘 적용해보심이 좋을 듯 싶습니다.

logo는 사이트를 대표하는 이미지입니다. 이때 logo를 적용할 때, 고려해야하는 요소가 있습니다. 요청한 디바이스에 따라, 서빙되는 로고의 해상도를 세분화하시는 것도 좋아보입니다. 작은 기기에 큰 해상도의 logo를 전달한다면, 서빙하는 파일의 크기가 증가할 수 있습니다. 이때 logo는 html의 해더에서 파싱될때 요청됩니다. 그런데 logo의 용량이 크다면, 추후 요청될 이미지나 기타 파일의 로딩이 느려질 수 있습니다. 즉, 병목이 발생할 수 있다는 것이죠. 따라서 작은 기기에는 작은 해상도의 logo를 큰 기기에는 큰 해상도의 logo를 전송하여, 필요한만큼의 해상도를 전송할 수 있도록 하는 것이 중요할 듯 싶습니다. 다시말해 전문적으로 프론트엔드를 구성하시고 싶다면, 디바이스 별로 다른 해상도의 logo 이미지를 서빙하는 것도 좋아보입니다.

(사실 favicon을 둥글게 다듬어서 서빙하는 것이 더욱 좋다고 판단합니다. 저도 적용 안했습니다. 바빠요. ㅎㅎ)

## 3. manifest.json

프론트엔드에서의 manifest.json은 브라우저가 웹사이트를 앱처럼 설치하고 실행할 수 있도록 필요한 정보를 제공합니다. 예컨데 스마트폰에서 특정 웹페이지를 바탕화면에 추가하여 앱처럼 사용할 수 있습니다. 이때 해당 앱이 어떻게 보여질지 등을 결정하는 것이 manifest.json입니다. 더하여 logo의 종류와 해상도에 따라 어느 경로로 서빙하는지 정보를 제공하기도 합니다. 

다음은 저의 블로그에 적용된 예시입니다.

```json
{
  "short_name": "j93es blog",
  "name": "j93es blog",
  "icons": [
    {
      "src": "/logo/favicon.ico",
      "sizes": "256x256",
      "type": "image/x-icon"
    },
    {
      "src": "/logo/logo192.png",
      "type": "image/png",
      "sizes": "192x192"
    },
    {
      "src": "/logo/logo512.png",
      "type": "image/png",
      "sizes": "512x512"
    }
  ],
  "screenshots": [
    {
      "src": "/logo/logo512.png",
      "sizes": "512x512",
      "type": "image/png",
      "form_factor": "wide",
      "label": "Logo"
    },
    {
      "src": "/logo/logo512.png",
      "sizes": "512x512",
      "type": "image/png",
      "form_factor": "narrow",
      "label": "Logo"
    },
    {
      "src": "/logo/j93es-logo.svg",
      "sizes": "200x100",
      "type": "image/svg",
      "label": "Logo"
    }
  ],
  "start_url": ".",
  "display": "standalone",
  "theme_color": "#f5f8ff",
  "background_color": "#f5f8ff"
}
```

기본 템플릿 그대로 사용하시는 경우도 있으실텐데요, 한번쯤은 신경쓰셔야할 파일이라고 생각합니다. 프론트엔드에서는 단순 기능 구현 또한 중요하지만, 남들과 차별되는 강점을 가지시려면 사소한 디테일을 챙기는 것이 중요하다고 생각합니다.

## 4. noscript

여러분의 디바이스의 브라우저는 자바스크립트 실행을 허용하나요? 대부분 허용할 것입니다. 그런데 자바스크립트 실행을 허용하지 않는 경우도 있지 않을까요? 자바스크립트 실행이 허용되지 않는다면, 웹사이트가 제대로 동작하지 않을 것입니다. 그렇다면 자바스크립트 실행을 허용하지 않는 환경에서는 어떤 페이지를 전달하는 것이 타당할까요? 바로 noscript 페이지입니다. 예를 들기 위하여 index.html의 head 태그를 살펴봅시다.

```html
<!DOCTYPE html>
  <head>
    <noscript>
      <meta
        http-equiv="refresh"
        content="0; url=/noscript-page/noscript.html"
      />
    </noscript>
  </head>
```

위와 같이 head 태그안의 noscript 태그가 있습니다. 만약 브라우저의 환경이 자바스크립트 실행을 허용하지 않는다면, 브라우저는 meta 태그의 경로로 noscript 페이지를 다시 요청하여 적절한 페이지를 노출시킵니다. noscript 페이지를 커스텀하여 사용하는 것 또한 고려해봄직합니다.

## 5. custom error page

에러 페이지와 기본 페이지 간의 디자인 통일성을 유지하는 것이 완성도 높은 웹페이지라고 말할 수 있지 않을까요? 간혹 발생하는 에러에 대하여 웹페이지는 에러를 알리는 페이지를 표출하기도 합니다. 그런데 리버스 프록시 유틸리티 등에서 기본적으로 제공하는 에러 페이지를 그대로 사용하는 경우 또한 있습니다. 하지만 완성도 높게 프론트엔드를 구성하시고 싶다면, 에러페이지를 커스텀하여 사용하는 것 또한 중요하다고 생각합니다.

더하여 단순히 React 내에서 에러페이지를 띄운다면, Soft 404 등의 사소한 SEO 관련 문제가 생길 수 있습니다. 즉, 에러에 대한 SEO를 고려하고 싶으시다면, 백엔드 측에서 직접적으로 에러 페이지를 전달하는 것이 더욱 좋습니다. 왜냐하면 프론트엔드에서 에러페이지를 랜더링한다면, HTTP 응답코드가 400이나 500번 대가 아닌 200번대로 전달될 것입니다. 하지만 백엔드에서 에러페이지를 전달한다면, 응답코드를 명확히 할 수 있겠죠. 그렇다면 Soft 404에 대한 이슈 등은 해결될 것입니다. 이와 관련하여 블로그 에러핸들링 포스팅에서 더욱 자세히 다룰 예정입니다.

## 6. 기본 배경색

CSS에는 웹페이지 요소의 배경색을 지정할 수 있는 CSS property가 있습니다. 이는 background-color입니다.

그런데 특정 사이트를 들어가본다면, 위로 스크롤 시에 흰색이 보이는 경우가 있습니다. 이는 대체적으로 바람직하지 않다고 판단됩니다. 헤더의 색과 상충되는 경우에 웹페이지가 단절된 느낌이 강하다면, 이는 사용자 경험에 좋지 않다고 판단됩니다.

이때 body 태그에 background-color를 지정해주는 것이 좋다고 판단됩니다. 웹사이트의 배경색을 지정한다면, 디자인적으로 통일감있고, 균형잡혀보일 수 있다고 생각합니다.

## 7. loading spinner 관련 로직

사용자 경험을 위하여 리소스 요청 시에 로딩 스피너를 이용하곤합니다. 저의 경우에도 블로그의 리소스 로딩시에 로딩 스피너를 표출해야하는 상황이었습니다. 이때, UI설계에서 로딩 이벤트를 어느 컴포넌트에서 처리할지 결정하지 않고 개발을 진행하였습니다. 이로 인하여 이벤트 리스너를 listening하는 컴포넌트의 선정을 고려하지 않고 개발하였습니다. 즉, 개발과정에 차질이 생겼습니다.

UI를 설계할 때에 로딩 스피너를 어느 컴포넌트에 언제 랜더링 시킬지를 명확히 하지 않는다면, 추후 설계에서 로딩 이벤트가 적절하게 구현되지 않을 수 있습니다. UI를 셜계하기 전에 로딩 스피너를 어느 컴포넌트에 언제 랜더링 시킬지 명확히 결정하고 구현하시는 것도 좋아보입니다.

더하여 로딩 스피너가 뚝뚝 끊기면서 랜더링 되었습니다. 저의 블로그는 여러 리소스를 서버에 요청합니다. 예를 들어 Dynamic import로 쪼개놓은 JS나 posting 목록을 말이죠. 이때, 여러 요청이 릴레이될 때, 로딩이 시작되고 중단됨이 반복되며, 로딩 스피너가 중간까지 갔다가, 다시 로딩 스피너가 처음부터 시작되며, 뚝뚝 끊기듯이 랜더링 되었습니다.

이에 대한 해결책에는 여러가지가 있을 수 있습니다. 예를 들어 로딩 이벤트가 적어도 몇 초 동안은 켜져있게 하는 등의 예시가 있을 것입니다. 하지만 이것이 사용자 경험에 최선은 아니라고 생각합니다. 사용자마다 디바이스, 네트워크 환경이 다릅니다. 이러한 이유로 로딩 스피너를 최소 몇 초 동안은 랜더링 시키는 것이 최선은 아니라고 판단하였습니다. 

제가 생각한 최선의 해결책은 "끊기지 않는 느낌만 주자"였습니다. 결국 문제는 로딩 스피너가 중간까지 돌아가다가 다시 처음으로 돌아가는 현상이였습니다. 따라서 중간에 요청되는 Dynamic import 된 JS 파일은 로딩 스피너를 송출하지 않는 방향으로 개발하였습니다. 이를 통하여 초기버전보다 훨씬 부드럽게 로딩 스피너가 랜더링되었습니다.(유지보수성을 조금 더 고려했어야했던 해결이 아니었나 싶습니다. 예를 들어 JS를 더 나누거나, 하위 페이지를 더 만든다면 로딩 스피너 이벤트를 더 손봐야하지 않을까 싶네요.)

## 8. 브라우저는 웹사이트의 언어를 어떻게 파악할까?

웹사이트를 크롬 브라우저에서 이용할 때, 영문 사이트 접근 시에 한국어로 번역 기능을 한번쯤은 살펴보셨으리라 생각합니다. 그런데 이 사이트가 영문인지 한국어인지 확인하는 방법은 무엇일까요?

바로 html의 헤더에 위치한 `<meta http-equiv="content-language" content="ko" />`를 통하여 해당 페이지의 언어를 파악합니다.

그런데 이를 잘못 적어두면 어떤 일이 발생할까요? 웹사이트의 언어가 한국어인데, meta 태그에는 영어로 적혀있다고 가정해봅시다. 그렇다면 크롬 번역 기능 등을 이용할 때에 한국어임에도 "영문 -> 한국어" 기능이 표출되어, 사용자 경험에 악영향을 미칠 수 있다고 판단합니다. 즉, meta 태그에 해당 사이트의 언어를 잘 적어두는 것이 중요하겠다고 판단합니다. 

## 9. 새 탭에서 링크열기

블로그에서 글을 쓰다보면, 링크를 첨부해야할 경우가 있습니다. 이때, 새탭에서 다른 도메인의 링크가 열리는 것이 사용자 경험에 좋다고 판단하였습니다. 

블로그 포스팅에서 다른 도메인 링크를 확인하고, 다시 블로그의 포스팅에 돌아오는 것을 가정해봅시다. 블로그 포스팅의 탭과 다른 도메인 탭이 둘 다 브라우저에 있다면, 블로그 포스팅에 다시 돌아오기가 편할 것입니다. 반면, 블로그 포스팅 탭이 다른 도메인 탭으로 변한다고 가정해봅시다. 그런데 다른 도메인의 탭에서 하위 path로 접속하였다면, 블로그 포스팅으로 돌아오는데에 편할까요? 아닐 것입니다.

즉, 새탭에서 다른 도메인의 링크가 열리는 것이 사용자 경험에 좋다고 판단하였습니다. 이를 위하여 새탭에서 링크가 열리도록 a 태그를 구성하고자 하였습니다. 이는 a 태그에 `target="_blank"`를 추가하는 방식으로 구현가능합니다.

그런데 `target="_blank"`시에 보안과 정보보호와 관련한 사항을 고려해야합니다. `rel` 속성에 2가지를 추가하면 됩니다. 첫째로 `noopener`입니다. 이 속성은 새 탭에서 열린 사이트가 원래 있던 사이트의 제어권을 갖지 못하게 막아줍니다. 예를들어 새탭에서 열린 링크가 악성 사이트였을때, 악성 사이트가 원래 페이지를 가짜 화면 등으로 바꾸는 공격(Tabnabbing)을 방지합니다. 둘째로, `noreferrer`입니다. 링크를 타고 들어간 사이트에서 사용자가 어디서 왔는지(이전 페이지 주소) 알 수 없도록 HTTP 리퍼러(Referer) 정보를 보내지 않습니다.

아래와 같이 a 태그를 랩핑하는 태그를 통하여 일관되게 구현가능합니다.

```tsx
const ExternalLink: React.FC<ExternalLinkProps> = ({
  href,
  children,
  ...props
}) => {
  return (
    <a href={href} target="_blank" rel="noopener noreferrer" {...props}>
      {children}
    </a>
  );
};
```

## 10. CSP 설정

CSP는 컨텐츠 보안 정책의 준말입니다. 이는 XSS(콘텐츠 주입 공격)을 막기 위하여 존재합니다. 예를 들어봅시다. 추후 블로그에 댓글 기능을 추가할 수도 있습나다. 그런데 공격자가 댓글에 다른 도메인에서 무언가를 다운받는 `<script>` 태그를 넣고 댓글을 작성하였습니다. 이때 피해자가 이런 댓글을 열어볼때, 다른 도메인에서 무언가를 다운받는 코드가 임의로 실행될 수 있습니다. 즉, 허용되지 않은 origin에서 다운된 스크립트 태그를 브라우저가 실행하지 않도록하는 것이 CSP입니다.

즉, CSP는 웹사이트의 JS, 이미지, 폰트, css 등이 다운되고 실행될 수 있는 origin을 지정하는 것입니다.(이미지나 CSS는 JS 실행의 여지가 없다고 판단되는 경우도 있겠습니다. 하지만 체이닝을 통하여 JS를 실행시키는 경우도 있으니, 최소한의 방어를 위하여 CSP를 모든 리소스에 잘 적용해두는 것도 좋아보입니다.) CSP는 HTML의 헤더나 HTTP(S) 요청의 응답 헤더에 포함될 수 있습니다. 저의 블로그에는 응답 헤더에 다음과 같은 CSP가 적용되어 있습니다.

``` txt
default-src 'none'; base-uri 'self'; connect-src 'self' cloudflareinsights.com; font-src 'self' cdnjs.cloudflare.com; form-action 'self'; frame-ancestors 'none'; img-src 'self'; script-src 'self' static.cloudflareinsights.com; style-src 'self' cdnjs.cloudflare.com; manifest-src 'self'; object-src 'none'; upgrade-insecure-requests
```

더하여 이러한 CSP에 unsafe-inline 속성이 적용된다면 브라우저는 html 내부의 인라인 script를 실행시킬 수 있으니, 왠만하면 사용하지 않는 것이 좋아보입니다. unsafe-inline 속성을 사용하지 않기 위하여 hash 등의 난수를 이용할 수는 있는데, 매 요청마다 갱신하는 것이 중요합니다. 즉 요청 헤더나 HTML 헤더의 CSP에 `{nonce}`를 포함하고 스크립트 태그에도 `<script nonce="{nonce}">`의 난수를 포함하여 무결성을 검사하는 것입니다.

이러한 CSP가 지정된다면 브라우저는 이 CSP에 의거하여 리소스를 실행하거나 적용할니다. 사실 CSP는 모든 XSS 공격을 방어할 수는 없습니다. 하지만 최소한의 방어 조치이니 적용하는 것이 좋아보입니다. 다만 새로운 리소스를 적용할 때에 CSP 위반으로 해당 리소스가 적용되지 않을 수도 있습니다. 따라서 다른 도메인 이용을 최소화하고(폰트도 직접 서버나 하나의 CDN에서 전송), hash 등의 nonce를 이용하여 콘텐츠를 전송하는 시스템을 구축한다면, 유지보수적으로도 좋아보입니다.

## 11. 정보보호정책

서버에 저장된 로그에 사용자의 정보가 어떻게 보호되는지 사용자가 알 권리가 있다고 판단합니다. 따라서 공신력 있는 사이트는 사용자의 정보가 어떻게 관리되는지 고시하곤합니다. 이는 사용자에게 웹사이트에 대한 신뢰를 줄 수 있습니다. 저의 사이트는 다음과 같은 목차로 구성되어있습니다.

- 개요
- 수집되는 정보
- 수집 목적
- 정보 보관 기간
- 정보 제공
- 정보 보호
- 정보 파기 절차 및 방법
- 문의

이러한 사용자의 정보를 보호하는 정책에는 기본적인 틀이 있습니다. 보안 정책을 공부하실 생각이 있으시다면, 비슷한 부류의 기본적인 정책의 틀을 먼저 파악하고 읽어보시는 것을 추천합니다.

또한 개인정보인지 아닌지 파악하는 것 또한 중요합니다. 개인정보는 살아 있는 개인에 관한 정보로서 개인을 알아볼 수 있는 정보이며, 해당 정보만으로는 특정 개인을 알아볼 수 없더라도 다른 정보와 쉽게 결합하여 알아 볼 수 있는 정보를 포함합니다. 이떼 사이트가 개인정보를 다룬다면, 법적인 규제가 적용될 수 있습니다. 

저의 블로그는 개인정보를 다루지 않아(IP의 경우에는 아직 제도가 명확하진 않습니다.) 법적인 규제가 없다고 판단합니다. 하지만 개인정보를 다룬다면, 이는 법적인 규제 또한 살펴보시는 것이 중요합니다.

## 12. 캐시 검증헤더

리소스가 변경되었는지 확인하는 효율적인 방법이 있을까요? 리소스 전부를 일일히 비교하는 방법도 있을 것입니다. 하지만 이는 굉장히 비효율적이라고 생각합니다. 

그런데 변경을 알려주는 지표가 있다면 그 지표만을 비교하면 되지 않을까요? 예를 들어 봅시다. HTTP 요청의 응답헤더에는 ETag와 Last-Modified 항목이 있습니다.(혹은 HTML meta 태그에 해당 내용을 포함하는 경우도 있습니다.) 이때 1일에 수정된 리소스에 `etag: {nonce-a}, lastmod: "1"`을 적용해볼 수 있습니다. 즉, 서버 측에서 적절히 해당 값을 갱신한다면, 해당 값만 비교해서 리소스의 변경 여부를 확인할 수 있습니다. 더하여, 응답 헤더만을 요청하여 더욱 효율적으로 콘텐츠 변경을 확인할 수 있을 것입니다.
